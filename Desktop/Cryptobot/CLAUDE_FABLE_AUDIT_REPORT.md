# TBX Trade Terminal — Аудит (Claude Fable)

> Аудит проведён по реальному коду репозитория (`Desktop/Cryptobot`), а не только по описанию.
> Каждое утверждение проверено; часть заявленных проблем скорректирована, найдены новые, более серьёзные.

---

## Важные поправки к исходному списку проблем

Прежде чем давать рекомендации — три факта, где реальность отличается от описания:

1. **Заявленный баг №7 (PATCH /users/me не сохраняет изменения) — НЕ подтверждён.**
   `get_db` коммитит сессию в конце каждого запроса (`backend/app/core/database.py:29`), поэтому
   присвоение `username`/`email` в `users.py:51-57` персистится. **Реальный** data-loss баг рядом:
   `PUT /me/exchange-keys` (`users.py:67-77`) — колонка `exchange_keys_encrypted` это обычный `JSONB`
   без `MutableDict`. При добавлении **второго** ключа биржи словарь мутируется на месте и
   присваивается тот же самый объект — SQLAlchemy не видит изменения, UPDATE не выполняется,
   ключ молча теряется. То же с `DELETE /me/exchange-keys/{exchange}` (`users.py:116-117`), когда
   после удаления остаются другие ключи.

2. **Сигнальный движок сканирует ТОЛЬКО BTC/USDT.** Хуже, чем заявленные «два WebSocket».
   `collector.py:194-195`: `for symbol in TRADE_SYMBOLS: await _watch_and_signal_symbol(...)` —
   но внутри `_watch_and_signal_symbol` бесконечный `while True` (строка 208), который никогда не
   возвращается. ETH, SOL, XRP, DOGE не сканируются вообще. Продукт «5 монет» на деле — 1 монета.

3. **Монетизация фактически отключена тремя независимыми багами** (см. P0-2 ниже): пользователь
   платит 29 ₽ вместо $29, подписка никогда не истекает, а сигналы доступны вообще без авторизации.

## Раздел 1: КРИТИЧЕСКИЕ ИСПРАВЛЕНИЯ (Must Fix Before Production)

### P0 — блокеры (без этого запускать нельзя никому, кроме себя)

**P0-1. ENCRYPTION_KEY: случайный ключ на каждый рестарт.**
- Файл: `backend/app/core/security.py:13-15`.
- Риск: после первого же редеплоя все ключи бирж всех пользователей нерасшифруемы; автоторговля мертва, пользователи вводят ключи заново (и теряют доверие).
- Решение — fail-fast вместо тихого фолбэка:
  ```python
  def _get_fernet() -> Fernet:
      if not settings.ENCRYPTION_KEY:
          raise RuntimeError(
              "ENCRYPTION_KEY is not set. Generate once with: "
              "python -c \"from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())\""
          )
      return Fernet(settings.ENCRYPTION_KEY.encode())
  ```
  Плюс в `.env.example` заменить пустое `ENCRYPTION_KEY=` на комментарий с командой генерации. Тот же fail-fast нужен для `SECRET_KEY` (сейчас в проде может остаться дефолт `change-me-...` из `config.py:16` → подделка JWT).

**P0-2. Биллинг не собирает деньги. Три бага:**

  a) **Цены в USD, списание в RUB.** `PLAN_PRICES` = 29/79/149 (`models/subscription.py:36-42`), `get_plan_price` возвращает их как есть (`services/payments/yookassa.py:193-194`), а платёж создаётся с `currency: "RUB"` (`yookassa.py:45`) и подписи «29 ₽» (`api/v1/payments.py:86-87`). Пользователь покупает месяц Trader за 29 рублей (~$0.35).
  Решение: один источник истины с явной валютой:
  ```python
  PLAN_PRICES_USD = {TRADER: Decimal("29"), INVESTOR_PRO: Decimal("79")}
  PLAN_PRICES_RUB = {TRADER: Decimal("2900"), INVESTOR_PRO: Decimal("7900")}
  ```
  и `get_plan_price(plan, currency)`.

  b) **Подписка никогда не истекает.** `require_active_subscription` (`api/deps.py:83-92`) проверяет только `status IN (active, trial)`, не `expires_at`. А единственное, что могло бы переводить статус в `expired` — Celery-воркеры — не запускаются нигде (нет ни в `docker-compose.yml`, ни в lifespan; `workers/*.py` — заглушки по 8-18 строк). Один платёж = пожизненный доступ.
  Решение: (1) добавить в запрос `Subscription.expires_at > datetime.now(timezone.utc)`; (2) фоновый asyncio-цикл в lifespan (раз в час) — `UPDATE subscriptions SET status='expired' WHERE status IN ('active','trial') AND expires_at < now()`.

  c) **Бесплатный доступ по самообъявленной рефералке.** `deps.py:80-81`: любая непустая строка в `user.referred_by` = вечный бесплатный доступ. Поле нигде не верифицируется. Решение: `referred_by` выставляется ТОЛЬКО процессом верификации UID (раздел 6), у пользователя нет прямого API для записи этого поля.

**P0-3. SELL-сигналы математически сломаны (тейки выше входа, вход не с той стороны).**
- `services/strategies/smc.py:446-454`: `_find_targets` всегда строит `entry + risk*N` — для SELL цели дороже входа.
- Там же `smc.py:432-436`: `_find_entry` игнорирует `direction` — SELL-вход ставится в ту же OTE-зону 0.618–0.786 от ретрейсмента high→low, т.е. в **discount** (ниже середины диапазона), тогда как шорт по SMC входит из **premium**.
- Решение:
  ```python
  def _find_targets(self, entry: float, stop: float, direction: str) -> list[float]:
      risk = abs(entry - stop) or entry * 0.01
      sign = 1 if direction == "BUY" else -1
      return [round(entry + sign * risk * m, 4) for m in (3, 5, 7)]
  ```
  и для SELL-входа считать OTE от противоположного конца диапазона: `entry_sell = (fib[0.382] + fib[0.214…])` — проще всего: зеркально, `high - (high - low) * 0.7` → зона 0.618–0.786 **вверх** от low. Добавить unit-тест: «для SELL все TP < entry < SL».
- Дополнительно проверить инверсию FVG-логики: `_evaluate_buy` (smc.py:357) даёт бонус за нахождение цены в **BEARISH** FVG, `_evaluate_sell` (smc.py:403) — в **BULLISH**. В классическом SMC ретест bullish FVG — лонговый сетап. Либо это осознанная логика «вход из имбаланса против ретрейса», либо инверсия — нужен осознанный выбор и тест.

**P0-4. Сканируется только BTC.**
- `services/market_data/collector.py:192-195` + бесконечный цикл в `_watch_and_signal_symbol` (208).
- Решение:
  ```python
  async def watch_and_signal_loop():
      exchange = ccxt_pro.binance({"enableRateLimit": True})
      await asyncio.gather(*[
          _watch_and_signal_symbol(exchange, s) for s in TRADE_SYMBOLS
      ])
  ```
  Заодно: убрать `fetch_ohlcv(500)` на каждую свечу (`collector.py:116`) — держать в памяти deque на 500 свечей на символ, инициализировать одним REST-запросом на старте, дальше пополнять из `watch_ohlcv`. И убрать сброс `retry_delay = 5` в `finally` (`collector.py:164-165`) — он ломает экспоненциальный backoff.

**P0-5. CryptoCloud webhook: платёж принят — подписка не та или не выдана.**
- `api/v1/payments.py:437`: `Decimal(str(data.get("amount", 0)))` — при `"amount": null` это `Decimal("None")` → `InvalidOperation` → 500 → CryptoCloud ретраит, пользователь без подписки.
- `payments.py:448`: `plan_str in SubscriptionPlan.__members__` сравнивает lowercase-значение (`"investor_pro"`) с UPPERCASE-именами (`"INVESTOR_PRO"`) → условие всегда ложно → **любой платёж активирует TRADER**, даже если заплатили $79 за Pro.
- `payments.py:451-453`: несовпадение суммы только логируется — заплатить можно $1.
- Решение:
  ```python
  try:
      amount_received = Decimal(str(data.get("amount") or "0"))
  except InvalidOperation:
      return {"status": "bad amount"}

  try:
      plan = SubscriptionPlan(plan_str)
  except ValueError:
      return {"status": "bad plan"}

  if amount_received < expected_amount - Decimal("0.01"):
      logger.warning(...)
      return {"status": "underpaid"}
  ```

### P1 — критичные

**P1-1. Исполнение на Bybit: позиция без стопа и без записи в БД.**
- `api/v1/signals.py:134-165`. Три проблемы:
  1) Ордер создан (стр. 134) → потом запись Trade (стр. 153). Падение БД = позиция-сирота.
  2) SL/TP ставится **вторым** ордером типа `"stop_loss"` — это невалидный unified-тип ccxt для `create_order` на Bybit; исключение проглатывается `except: logger.warning` (стр. 164-165) → **позиция остаётся без стоп-лосса молча**. Для трейдинг-продукта это худший из возможных отказов.
  3) `signal.symbol` = `"BTC/USDT"` (спот). Шорт на споте без заёмных средств не исполнится; деривативный символ — `"BTC/USDT:USDT"`. SELL-сигналы неисполнимы в принципе.
- Решение: один атомарный ордер с SL/TP в параметрах (Bybit это поддерживает):
  ```python
  order = await exchange.create_order(
      symbol, "market", side, size, None,
      {"stopLoss": stop_loss_price, "takeProfit": tp_price, "category": "linear"},
  )
  ```
  Порядок записи: сначала `Trade(status=PENDING)` + commit → ордер на бирже → `status=OPEN`, `order_id` + commit. При падении второго шага — reconciliation-цикл (раз в минуту сверяет PENDING-трейды и открытые позиции через `fetch_positions`). Переход на `"BTC/USDT:USDT"` + `category=linear`, иначе шорты выбросить из продукта.

**P1-2. Потеря ключей биржи (JSONB-мутация)** — см. «поправку №1» выше.
- Решение (одна строка на модель): `exchange_keys_encrypted: Mapped[dict | None] = mapped_column(MutableDict.as_mutable(JSONB), ...)` — либо в эндпоинтах `current_keys = dict(current_user.exchange_keys_encrypted or {})` (новый объект).

**P1-3. Сигналы — публичные.** `GET /signals`, `/signals/latest`, `/signals/{id}` (`signals.py:21-77`) не требуют даже логина. Ядро платного продукта отдаётся анонимно. Решение: `CurrentUser` минимум; для не-подписчиков — задержка 24 ч (фильтр `created_at < now() - interval '24h'`), это же — основа free-тарифа.

**P1-4. Аутентификация:**
- Нет rate-limit на `/login`, `/register` (`auth.py:73-140`) — брутфорс. Решение: `slowapi` или счётчик в Redis (5 попыток / 15 мин на IP+email), ~30 строк.
- Reset-токен бессрочен: `reset_password` (`auth.py:258-277`) не проверяет `email_verification_sent_at`. Добавить TTL 1 час.
- Фронтенд: токен в `localStorage` (`frontend/src/lib/api.ts:8`), refresh-токен вообще не используется (логин сохраняет только access, стр. 108-114) — сессия умирает через 60 минут, и это XSS-чувствительно. Решение: refresh в httpOnly cookie + interceptor с ретраем 401 через `/token/refresh`.

**P1-5. `exchange.py` падает при импорте без ccxt.** `services/trading/exchange.py:15-19` — `EXCHANGE_MAP` обращается к `ccxt_async.binance` на уровне модуля; при `ccxt_async = None` — `AttributeError` при импорте, а не осмысленная ошибка. Решение: строить карту лениво внутри `create_exchange_client` или `EXCHANGE_MAP = {} if not CCXT_AVAILABLE else {...}`.

### P2 — важные

- **Индексы:** `signals(symbol, created_at DESC)`, `signals(created_at DESC, confidence)`, `trades(user_id, status)`, `subscriptions(user_id, status)` — одна alembic-миграция.
- **`Signal.executed` — глобальный флаг** (`trade.py:92`): первый исполнивший пользователь блокирует сигнал для всех остальных (`signals.py:92-93`). Убрать флаг, проверять «есть ли у ЭТОГО пользователя Trade по этому signal_id».
- **Два `Base(DeclarativeBase)`:** `core/database.py:21` и `models/base.py:9`. Все модели используют второй; первый удалить, импортировать Base из models.
- **`risk_per_trade_pct` — мёртвая настройка:** читается из `bybit_keys` (`signals.py:116`), но `ExchangeKeySet` (`schemas/user.py:60-64`) её не принимает — всегда 2.0. Либо добавить поле в схему, либо убрать иллюзию настройки из фронтенда.
- **PnL не считается при закрытии:** `close_position` (`signals.py:294-298`) не пишет `exit_price`/`pnl` — история трейдов бесполезна. Взять `average` из ответа `create_order` закрытия.
- **Несоответствие таймфреймов:** `SMCStrategy.timeframe = "4h"` (`smc.py:459`), данные — 1h (`collector.py:22`). Привести к одному, параметры (SWING_LOOKBACK=5 и min_rr=2.0/3.0 — расходятся между конструктором и коллектором) — калибровать под фактический ТФ.

## Раздел 2: УПРОЩЕНИЕ АРХИТЕКТУРЫ

**2.1. Два бота → один (backend-бот), но с переносом работающих фич.**
Оба на `python-telegram-bot` (root: v22 + GPT-4o + Google Sheets; backend: модульный + DeepSeek + PostgreSQL) — портирование дешёвое. root `bot.py` (2982 строки) — это работающий бизнес, его нельзя просто выключить, но и развивать два нельзя. План:
1. Заморозить root `bot.py` (только hotfix).
2. Перенести в backend-бот три вещи, которые реально нужны: приём UID рефералки (уже есть `handlers/payments.py: handle_uid_submission` — довести до БД вместо Sheets), CryptoCloud-оплату, vision-анализ скриншотов.
3. Единые цены из `PLAN_PRICES` (сейчас root: $25/$199 lifetime vs backend: $29/$79 — два прайса на один продукт).
4. Выключить root-бот, Google Sheets оставить как read-only архив.
Экономия: ~3000 строк дублирующегося кода, один прайс, одна БД. Оценка: 4-6 дней в спринте 3.

**2.2. Celery — удалить целиком.** `workers/` — 92 строки заглушек, брокер не запущен, задачи не написаны. Для 5 символов и сотен пользователей достаточно asyncio-тасков в lifespan (образец уже есть — collector). Нужно всего 2 периодические задачи: expiry-подписок (P0-2b) и reconciliation трейдов (P1-1). Это ~60 строк вместо инфраструктуры Celery+beat+flower. Экономия: минус зависимость, минус контейнер, минус класс проблем.

**2.3. Платёжки: оставить CryptoCloud, YooKassa — за фиче-флаг.**
Аудитория — крипто-СНГ, деньги у неё в USDT. YooKassa тянет за собой: юрлицо РФ, НДС, чеки, рекуррентные списания, инвойсы (`payments/invoicing.py`, `recurring.py`, `Invoice`-модель — там, кстати, `vat_rate=4`, а `vat_amount = price * 0.20`, и `total = price` без НДС — сломанная бухгалтерия, `payments.py:287-297`). Для 3-5 друзей это мёртвый груз. Не удалять — отключить роуты флагом `YOOKASSA_ENABLED=false`, вернуться при реальном спросе на RUB.

**2.4. Отрезать от MVP (скрыть роуты/меню, таблицы не трогать):**
- Модели/сервисы: `Portfolio`, `DCAPlan`, `PropFirmChallenge`, `Position` (не используется — позиции считаются по `Trade.status=OPEN`), стратегии `grid/dca_accum/trend` (нет ни одного вызова в проде), `services/prop_firm/`, `services/portfolio/`.

- Тарифы: 5 планов → 2 (см. раздел 5). `PROP_FIRM_MASTER` и `ENTERPRISE` из enum не удалять (миграция типов в PG болезненна), просто не показывать.
- Один AI-провайдер: DeepSeek ИЛИ GPT-4o (DeepSeek дешевле, качества для «объясни график» хватает). Сейчас — оба.
Экономия суммарно: ~30-40% поверхности кода перестаёт требовать внимания; высвобождает примерно 2 недели из 6.

**2.5. Что НЕ упрощать:** FastAPI+PG+Redis+Next.js — стек адекватный; PWA оставить; модульная структура backend-бота хорошая.

## Раздел 3: ПОВЫШЕНИЕ ЦЕННОСТИ ПРОДУКТА

Приоритет по соотношению «perceived value / трудозатраты»:

1. **Telegram-push сигнала в момент появления** (~1 день). Инфраструктура готова: `notify_signal` уже публикует в Redis `signals:new` (`collector.py:141`), бот уже живёт в том же процессе. Не хватает подписчика на канал + рассылки. Это фича №1: трейдер живёт в Telegram.
2. **SSE на дашборде вместо 30-сек polling** (~1 день): эндпоинт `GET /signals/stream`, читающий тот же Redis pub/sub, на фронте `EventSource`. Сигнал «появляется сам» — ощущение живого терминала.
3. **График с разметкой сигнала** (2-3 дня): TradingView `lightweight-charts` (бесплатная, 45 КБ), свечи 1h + горизонтальные линии entry/SL/TP + зоны FVG/OB из `signal.metadata_`. Без графика трейдер продукту не верит; это главный «вау».
4. **Причины сигнала на карточке** (полдня): metadata уже хранит trend/fib_ote — расширить до списка факторов («BOS вверх 4h», «цена в discount», «ретест OB»). Прозрачность = отличие от чёрных ящиков 3Commas/Cryptohopper.
5. **Paper-трейдинг** (1-2 дня): исполнение без ключей — `Trade(exchange="paper")` по текущей цене из Redis. Снимает страх на онбординге, даёт free-тарифу смысл, генерирует track record.
6. **Публичный track record** (1-2 дня): страница со статистикой сигналов (win rate, средний RR, исход каждого сигнала — задет SL или TP по истории цен). Продаёт лучше любого лендинга; конкуренты этого почти не делают честно.
7. **Онбординг за 3 шага, до 5 минут:** (1) вход через Telegram Login (уже есть `auth/telegram`) → (2) сразу видны живые сигналы (free — с задержкой) и paper-кнопка → (3) ключи Bybit просим только когда пользователь нажал «исполнить по-настоящему», с гайдом «какие права выдать ключу» (только trade, без withdrawal — и написать это большими буквами).
8. Мелочи с большим эффектом: шапка PnL (сегодня/7д/всё время); статус сигнала «истёк» (цена ушла от entry); комиссия и net-PnL в каждом трейде; бейджи confidence цветом; звук/вибрация в PWA.

Чего у конкурентов нет и что не надо догонять: не строить грид/DCA-ботов (там 3Commas непобедим). Ниша — «прозрачные SMC-сигналы с объяснением + исполнение в 1 клик».

## Раздел 4: ТОЧНОСТЬ И ПРОФЕССИОНАЛИЗМ ТРЕЙДИНГА

**4.1. SMC-движок, по убыванию важности:**
1. Починить SELL-геометрию (P0-3) — до этого всё остальное бессмысленно.
2. **Liquidity sweep вместо equal highs/lows:** сетап SMC — это снятие ликвидности (вик за equal highs/lows с закрытием обратно) + смена структуры. Детектор: `high[i] > liq_level && close[i] < liq_level` в пределах 1-2 свечей. Сейчас `detect_liquidity_levels` (smc.py:196-225) только находит уровни (O(n²) по свингам, к слову), но не событие снятия.
3. **Order Block с displacement:** требовать импульс — тело следующей свечи > 1.5×ATR(14) и учёт митигации (OB, уже протестированный ценой, невалиден). Сейчас (smc.py:159-193) — любой 3-свечной паттерн, шум.
4. **Валидация сигнала во времени:** сигнал с лимитным входом в OTE должен отменяться, если цена дошла до SL раньше entry, и истекать через N свечей. Сейчас сигнал живёт вечно.

**4.2. Multi-timeframe без переусложнения (~1 день):**
4h определяет bias (тренд по BOS/CHoCH), 1h даёт вход. Реализация: коллектор раз в 4 часа тянет 4h REST-ом (это +5 запросов/4ч — ничто), считает `htf_trend`; `generate_signal(df_1h, htf_bias=...)`: совпадение направления +15 confidence, противоречие −25 (или вето). Не строить полноценный 3-ТФ каскад — не сейчас.

**4.3. Regime filter — минимальная версия (~100 строк):**
- TREND: |EMA50 slope| > порога И ATR%(14) в норме → торгуем по тренду.
- RANGE: плоская EMA, цена пилит границы → торгуем только от краёв (или не торгуем).
- CHOP: ATR-percentile высокий при рваной структуре (частые ложные BOS) → сигналы подавляются.
Классификатор: EMA50-slope + перцентиль ATR + плотность BOS за 50 свечей. В metadata сигнала писать режим — это и фильтр, и объяснение для пользователя.

**4.4. Честный backtest (сейчас он опаснее его отсутствия).**
`strategies/base.py:40-111` содержит look-ahead и оптимизм:
- Вход по `signal.entry` (лимитка в OTE, часто далеко от рынка) считается исполненным мгновенно (стр. 60) — не проверяется, что цена вообще дошла до entry.
- SL/TP проверяются по `close` (стр. 67-87), внутрисвечные выносы по high/low игнорируются — SL занижен, TP завышен.
- Ноль комиссий/проскальзывания/фандинга.
Исправления: (1) вход только если следующие свечи прошли через entry (`low <= entry` для BUY); (2) SL/TP по high/low; если обе цели в одной свече — консервативно считать SL; (3) издержки: taker 0.055% × 2 (Bybit) + slippage 3-5 bps + funding ~0.01%/8ч на время удержания; (4) walk-forward: параметры на 2023, проверка на 2024-2025, отчёт по кварталам и по символам отдельно. Метрика — **expectancy после издержек**, не win rate (при RR≥3 нормальный win rate — 25-35%, к этому надо готовить и себя, и пользователей).

**4.5. Где учесть комиссии в живом исполнении:** поля `fee`, `fee_currency`, `funding_paid` в `Trade`; заполнять из ответа биржи (`order["fee"]`); net-PnL везде в UI. Одна миграция + 20 строк.

**4.6. Журнал трейдера — автоматический, это и есть фича:**
- В `Trade` добавить: `entry_reason: JSONB` (автоснимок metadata сигнала: тренд, режим, факторы, confidence), `exit_reason: str` (SL/TP/manual), `notes: Text`, `emotion: str|null` (опциональный тег: по плану / фомо / отыгрыш).
- UI: таблица трейдов раскрывается в карточку «почему вошёл (авто) / почему вышел / заметка».
- Ценность: пользователь получает дисциплинирующий журнал бесплатно, без ручного ввода — ни у одного из конкурентов в этой цене этого нет.

## Раздел 5: ТАРИФНАЯ СЕТКА

Для стадии «3-5 друзей → первые 100 пользователей» пять планов — вредная сложность. Схема:

| Тариф | Цена | Что входит |
|---|---|---|
| **Free** | $0 | Сигналы с задержкой 24 ч, paper-трейдинг, журнал, 1 биржа read-only |
| **Trader** | **$29/мес или $290/год** (2 мес в подарок) | Real-time сигналы + Telegram push, исполнение в 1 клик, риск-менеджер, журнал полностью |
| **Trader via Bybit** | $0 | = Trader, пока активна верифицированная рефералка и депозит ≥ $150 |

- **Pro ($79) сейчас не нужен** — под него нет фич (DCA/портфели вырезаны в разделе 2). Вернуть, когда появятся мульти-биржа/API/приватные стратегии. Якорем в прайсе может висеть «Pro — скоро», это работает не хуже.
- **Trial: 7 дней, автостарт при регистрации**, полный Trader, без карты. Код уже есть (`payments.py:343-376`) — вызвать создание trial-подписки прямо в `/register` вместо ручной кнопки. Напоминание в Telegram на день 5 и день 7.
- **Годовой: да** — $290 (экономия 17%, «2 месяца бесплатно»). Крипто-аудитория охотно платит USDT разово; годовые платежи решают и проблему churn.
- **Lifetime: нет.** $199 lifetime из root-бота — продажа бесконечной поддержки за 7 месяцев подписки. Существующим lifetime-покупателям — грандфазеринг, новых не продавать.
- **Free-тариф с задержкой — да** (задержанные сигналы + paper): это и воронка, и доказательство track record. Реклама — нет.
- **RUB:** если YooKassa включится — 2900 ₽/мес фикс (не привязка к курсу), отдельной строкой в PLAN_PRICES_RUB. Никогда не держать два прайса в двух ботах (сейчас: $25/$199 в root vs $29/$79 в backend).
- **Автонапоминание об истечении:** тот же scheduler-цикл, T-3 дня и T-0, через бот. Без этого продления не будет.

## Раздел 6: РЕФЕРАЛЬНАЯ ПРОГРАММА

Разделить две разные механики — сейчас они смешаны:

**A. Bybit-рефералка как способ оплаты (запустить в спринте 3).**
Механика уже наполовину есть (root bot: UID → Google Sheets → ручная проверка). Довести до автомата:
1. Таблица `referral_claims(id, user_id, exchange, uid, status: pending/verified/rejected, deposit_usd, verified_at, checked_at)`.
2. Пользователь шлёт UID (в боте или на дашборде) → `pending`.
3. Раз в час задача дёргает **Bybit Affiliate API** (`/v5/user/aff-customer-info` — аффилиату доступны данные привязанных UID: факт привязки, депозит, объём). UID найден и депозит ≥ $150 → `verified`, выставляется `user.referred_by = uid` (единственный путь записи этого поля — закрывает дыру P0-2c).
4. Ежемесячная перепроверка объёма: рефералка «живая», если объём ≥ $X/мес — иначе доступ переводится в trial-режим с предложением подписки.
Анти-фрод: UID уникален на всю таблицу (unique index); депозит проверяется по API, а не по скриншоту; один аккаунт — один UID.
Экономика: rebate Bybit (10-30% комиссий реферала) при интрадей-объёмах легко превышает $29/мес — это лучший тариф для обеих сторон.

**B. Пользовательская рефералка (не раньше, чем будет 100+ пользователей).**
Для 3-5 друзей строить её — трата времени. Когда понадобится, MVP на ~200 строк: `?ref=<code>` при регистрации → `referrals(referrer_id, referred_id, created_at)`; вознаграждение — 30% первого платежа (стандарт крипто-SaaS), выплата USDT, минимум $20; дашборд «кого привёл / сколько заработал». Саморефералы экономически бессмысленны при выплате только с реальных платежей; ручная модерация выплат до $100. Геймификация (уровни, бейджи, лидерборды) — не строить: при текущем масштабе это декорация.
